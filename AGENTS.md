# Архитектура

Пакеты по домену (вертикальные срезы), слои — внутри пакета.

- **Срез** `server/internal/<фича>/` — всё про фичу: HTTP, логика, валидация.
  Сейчас: `auth` (вход, сессии, пароли, аватары), `leads` (публичная форма
  заявок), `home` (витрина: главная со счётчиком, красивые адреса, статика).
- **`server/internal/store/`** — весь SQL и миграции, одна база. Общий слой
  осознанно: при одной SQLite разносить SQL по срезам = соединение и миграции
  в N местах.
- **`server/internal/webutil/`** — то, что нужно нескольким срезам: `ClientIP`,
  реестр лимитов `Limits`, проверка почты `ValidEmail`.
- **`server/internal/logging/`** — центральный логгер `*logging.Logger`:
  собирается в main, готовым приходит в `Config.Log` срезов.
- **`server/main.go`** — единственный файл в корне `server/` и единственный
  composition root: срезы создаются и связываются только тут, явным DI через
  конфиг-структуры.

Зависимости: срез → store; store ни про кого не знает. Срезы не знают друг о
друге: общее выносится в `webutil`/`store`, а не импортируется из соседа.
Интерфейс, нужный срезу, срез объявляет у себя (со стороны потребителя).
Логгер исключение: `*logging.Logger` идёт в `Config.Log` напрямую,
свой интерфейс под него и заглушка не плодятся.

## Добавление фичи

1. Миграция: новый `store/migrations/000N_описание.sql` (4 цифры).
2. SQL: методы в `store/<таблица>.go`, сантинелы store.
3. Срез: `server/internal/<фича>/` — тонкий `handlers.go` + логика,
   экспорт `New(Config)` и `Register(mux)`.
4. Сборка: +1 строка в `main.go`.

Фича про юзера (профиль, аватар) — расширять `auth`, не плодить срез.

## Тесты

- **Все** тесты живут в `internal/<пакет>/tests/`, `package <пакет>_test`.
  Внутри пакета рядом с кодом тестов нет: `ls <пакет>/` показывает только
  рабочие файлы.
- Только экспортное API; HTTP — через настоящий `Register`. Внутренности не
  экспортируются ради теста: сначала чёрный путь, потом если совсем безвыходно,
  рефакторинг по существу (вынести суть за экспортную границу), а не голый
  `export`.
- SQL — `internal/store/tests/`. Баг без падающего теста не исправлен.

## Комментарии

Агрессивно мало: комментарий оправдан, только если по коду он не читается.

- Оставить: doc у пакета (1-2 строки), у экспортных типов, интерфейсов,
  структур и их полей (1 строка, поле только если имя не объясняет формат/единицы),
  у экспортных функций (только когда поведение неочевидно из сигнатуры),
  и inline в тонких местах: инварианты безопасности, обходы драйвера SQLite,
  гонки, техдолг.
- Удалить: историю («раньше», «перенесено из», «в методичке», номера
  лабораторных), обоснования выбора и эссе, пересказ следующей строки кода,
  комментарии к очевидным вещам. Длинный абзац сжимать до одной строки.
- Длинное тире `—` (U+2014) и `–` (U+2013) запрещены везде в Go-файлах:
  в комментариях, строках, логах, `http.Error` и ожиданиях тестов. Вместо него
  запятая, двоеточие или точка. Диапазоны (`3–30`) — обычным дефисом (`3-30`).
  Исключение: применённые миграции `store/migrations/0001*` и `0002*` править
  нельзя (sha256), их комментарии остаются как есть. Проверка:
  `rg -n '[—–]' server | rg -v 'migrations/000[12]_'` — пусто.
- Если строка текста меняется, поправить все тесты, которые её ищут.
- Лимит на одну сущность: 1-2 строки на doc, 1 inline на тонкое место. Если
  получается абзац из 4+ строк — половина воды, сокращать.
- Если неясно, оставить комментарий или удалить: удалить. Проще читать код.

## Правила, которые легко сломать

- Применённые миграции не редактировать (sha256-контроль валит старт);
  изменение схемы — новый файл, down-скриптов нет.
- `context.WithoutCancel` — только для уже свершившихся действий (счётчик,
  журнал). Всё остальное — обычный ctx.
- Защита не «упрощается»: `no-store` на HTML, honeypot + Origin у формы заявок,
  CSRF у закрытого раздела, лимитеры, слушаем только 127.0.0.1 (наружу nginx).
- Лимит вешается middleware при регистрации маршрута, не внутри обработчика.
  Вся таблица бюджетов — в `main.go`: срез экспортирует имя бюджета, порог
  поднимается переменной `LIMIT_<БЮДЖЕТ>`.
- Текст ошибок SQLite не парсим: «занято / не занято» — уточняющими запросами
  и индексами.

## Проверки

`npm run lint` · `go test ./... -race` · `golangci-lint run ./...` ·
`npm run size` — всё зелёное, CI гоняет то же.

## Деплой

`.github/workflows/ci.yml`: отдельные job'ы на тулчейн — `format`, `css`,
`ts`, `go`, `shell`, `size` — и **deploy** только main, когда все job'ы
зелёные и `vars.DEPLOY_ENABLED == 'true'`. Feedback (имена шагов, echo,
вывод) — по-английски ключевое:

1. Статика — rsync; **юнит — `install` из репо** (иначе сервер живёт на
   unit файле старого релиза: `Environment=DATA_DIR` теряется, база ищется
   в readonly `/var/www`, сервис падает в restart loop); бинарник —
   `install` + `mv` (атомарный своп), прежний остаётся как
   `site-server.prev`. Сервис: systemd user unit, деплой ставит юнит,
   рестартит и читает лог сам, ни одного sudo.
2. **До рестарта** — снимок базы `site-server backup` (миграции только
   вперёд) и копия `site.db.pre-deploy`: откат возвращает бинарник и
   схему вместе, иначе `.prev` падает на `store.Open` и цикл
   `Restart=on-failure` держит сайт в 502.
3. Рестарт + smoke: витрина 200, закрытый раздел 303, чужие файлы и
   оглавления каталогов 404, счётчик +1 за запрос.

Ручной откат — workflow `.github/workflows/rollback.yml` (или вручную:
`stop && mv site-server.prev site-server && start`).

`public/js/main.js` закоммичен: правка `src/*.ts` без `npm run build:ts` =
красный CI. Новую страницу или статику добавлять в smoke-список деплоя.

## CI/CD, как расширять

- **Job на тулчейн**: новый линтер или проверка = один самодостаточный job
  (checkout, свой setup, один tool). Не сцеплять с соседним.
- **Плагинг деплоя в одном источнике**: `.github/actions/deploy` ставит
  ssh-ключ и публикует `SSH_*`, `DEPLOY_PATH`, `DATA_DIR`, `RESTART_CMD`,
  `TARGET`, `SSH_OPTS` в `$GITHUB_ENV`. Deploy и rollback делают `uses:` его
  и не копируют env. Смена пути или секрета = одна правка, дрейф `DATA_DIR`
  между юнитом и workflow'ами больше не возможен по построению.
- **Шаг деплоя**: `deploy/remote/<name>.sh` + тест в `deploy/tests/`, затем
  `uses: ./.github/actions/deploy-step` (`name` и нужные `KEY=VALUE`; путь и
  `restart_cmd` с пробелами не рвутся). Шагу, которому надо сначала положить
  файл (rsync юнита, бинаря) или посчитать значение (stamp, список
  smoke-url), остаётся обычный `run:`, что заканчивается тем же `run.sh`:
  так живут install-unit, swap-binary, backup-db, check-live.
- **Миграции**: `store/migrations/000N_*.sql`, только вперёд, sha256. На
  деплое безопасность даёт тройка: `dry-run` перед рестартом, снимок
  `site.db.pre-deploy`, парный `restore_db` в ролбэке (бинарь и база
  откатываются вместе). Ручной откат: `rollback.yml`.
- **smoke** = один список `deploy/smoke-urls.txt`, его читают и deploy, и
  e2e: новая страница или маршрут попадает в проверку сама.
- **e2e** репетирует deploy целиком на user-systemd, пока вне гейта
  `deploy.needs`: дрейф он ловит, но флак не блокирует прод.
