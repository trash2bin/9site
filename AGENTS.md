# Архитектура

Пакеты по домену (вертикальные срезы), слои — внутри пакета.

- **Срез** `server/internal/<фича>/` — всё про фичу: HTTP, логика,
  валидация (см. `auth`). Срезы не знают друг о друге.
- **`server/internal/store/`** — весь SQL, одна база, одна точка
  миграций. Общий слой осознанно: при одной SQLite разносить SQL по
  срезам = соединение и миграции в N местах.
- **`server/main.go`** — единственный composition root. Срезы создаются
  и связываются только тут, явным DI через конфиг-структуры.
- Зависимости: срез → store; store ни про кого не знает. Интерфейсы
  объявляет потребитель (`accept interfaces, return structs`).

Хорошая абстракция (интерфейс-граница между срезами, срез вместо
плоских слоёв) — цель, а не зло: она уменьшает связность и даёт держать
систему в голове. Единственный способ делать их правильно — границу
объявлять со стороны потребителя, а не со стороны реализации.

## Добавление фичи

1. Миграция: новый `store/migrations/000N_описание.sql` (4 цифры).
2. SQL: методы в `store/<таблица>.go`, возвращают сантинелы store.
3. Срез: `server/internal/<фича>/` (тонкий `handlers.go` + логика).
   Фича про юзера (профиль, аватар) — расширять `auth`, не плодить срез.
4. Сборка: +1 строка в `main.go`.
5. Тесты: логика — моки интерфейсов потребителя; SQL — `store/test/`;
   HTTP — `httptest`. Баг без падающего теста не считается исправленным.

## Правила, которые легко сломать

- Применённые миграции не редактировать: sha256-контроль валит старт.
  Любое изменение схемы — новый файл. Down-скриптов нет (откат =
  старый бинарник + бэкап `site.db`).
- Текст ошибок SQLite не парсим — различение «логин занят / почта
  занята» и т.п. делается уточняющими запросами и индексами.
- `context.WithoutCancel` — только для действий, уже свершившихся
  (счётчик визитов, журнал действий): обрыв соединения не должен их
  отменять. Всё остальное — обычный проброс ctx.
- Защитные флаги не убирать и не «упрощать»: `no-store` на HTML,
  honeypot + Origin-проверка форм, лимитеры, слушаем только
  127.0.0.1 (наружу — nginx).
- Код, сообщения и комментарии — по-русски. Ошибки: `fmt.Errorf("%w")`,
  сантинелы в store, `errors.Is` наверху.

## Проверки

`npm run lint` (gofmt, vet, TS, CSS) · `go test ./... -race` ·
`golangci-lint run ./...` · `npm run size` — всё должно быть зелёным,
CI гоняет то же самое.

## CI/CD

`.github/workflows/ci.yml`, две джобы.

**checks** — каждый push в main, PR, ручной запуск: фронт (prettier,
stylelint, typecheck, пересборка бандла и сверка закоммиченного
`public/js/main.js`) · бэк (gofmt, vet, golangci-lint, govulncheck,
тесты `-race`, сборка) · shellcheck · бюджет главной ≤ 64 КБ
(`SIZE_LIMIT`).

**deploy** — только push/workflow_dispatch в main, когда checks зелёный
и `vars.DEPLOY_ENABLED == 'true'` (GitHub environment `production`):

1. Linux-бинарник (`-trimpath -ldflags "-s -w"`) + rsync статики;
   `public/css|assets|js` катаются с `--delete-after` (мусор с прошлых
   разбивок не копится на сервере).
2. Бинарник ставится `install` + `mv` — атомарный своп: сервис не видит
   момент без файла и не падает с «Text file busy». На `cp` не менять.
3. После рестарта — smoke прямо на сервере: витрина 200, закрытый
   раздел 303, чужие файлы (`auth.db`, `main.go`, `visits.dat`) — 404,
   счётчик растёт ровно на 1 за запрос.

Правила:

- `public/js/main.js` — собранный бандл, он закоммичен; CI пересобирает
  и сверяет. Правка `src/*.ts` без `npm run build:ts` = красный CI.
- Новую страницу или статику добавлять в smoke-список деплоя — иначе
  её доступность после деплоя никто не проверяет.
