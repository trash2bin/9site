# Ivan's Little Web

Персональный сайт с ретро-оформлением Web 1.0, страницей по макету и фотоальбомом с умным фильтром.

![Главная страница сайта](docs/preview.webp)

## Запуск

Нужен Go 1.27 или новее (в `go.mod` зафиксирован toolchain go1.27.2 — на нём держатся фиксы уязвимостей stdlib).

```bash
DATA_DIR=var go run ./server
```

Сайт откроется по адресу <http://localhost:8080>. Остановить сервер: `Ctrl+C`.

## Страницы

- `/` — главная страница.
- `/maket` — отдельная страница, свёрстанная по макету.
- `/catalog` — фотоальбом с фильтрами по разделу, типу файла и ориентации. Список снимков приходит из базы (`GET /api/photos`). Недоступные варианты автоматически отключаются; печатный вид включается без перезагрузки.

## JSON API и OpenAPI

У фронта один вызов: `GET /api/photos` отдаёт весь альбом, разделы и теги
одним ответом, страница фильтрует его в браузере. Спека этого вызова
генерируется из Go-структур ответа:

```
npm run api:gen    # спека из Go-типов, затем src/api-types.ts из спеки
```

Перегенерация спеки — обычный golden-файл: тест `TestSpecFresh` сравнивает
`server/internal/api/openapi.json` с тем, что собирается из типов, и с флагом
`-update` перезаписывает файл

Всё про контракт лежит в одном пакете `server/internal/api`: структуры ответа
(`Photo`, `Section`, `PhotosResponse`), сборка спеки `BuildSpec`, сама спека
`openapi.json` и её отдача `Handler`. Срез `album` только заполняет эти
структуры. `src/model.ts` и `src/api.ts` не описывают форму ответа руками, а
берут её из `src/api-types.ts`, поэтому Go-структура, спека и фронт не
расходятся.
Проверки: тест `TestSpecFresh` падает, если спеку забыли перегенерировать (`npm run api:gen` лечит);
в CI джоба `ts` перегенерирует `src/api-types.ts` и падает на диффе, а
`gofmt`/`test` в джобе `go` ловят правку структур без спеки.

Сама спека закрыта логином: `GET /vault/openapi.json`, гость получает 303 на
`/studio?auth=login`, ответ `no-store`. Swagger UI не подключён: его бандл
(~1.5 МБ) не влезает в бюджет статики, а спека читается любым инструментом,
который умеет импортировать OpenAPI по URL.

- `/studio` — витрина закрытого раздела: открыта всем, показывает движ для авторизованных; вход и регистрация — во всплывающем окне.
- `/vault` — закрытый раздел: без входа сервер перенаправляет на окно авторизации (проверяется и тестами, и на деплое).
- `/vault/album` — загрузка кадров в фотоальбом: файл, подпись, раздел и список загруженного. Доступна после входа: свой кадр автор может удалить сам, чужой удаляет только админ.
- `/vault/users` — права пользователей: список аккаунтов и выдача роли админа. Открывается только админом.

## Разработка

Node.js нужен для проверок и сборки TypeScript в один компактный браузерный скрипт, но не для запуска сайта.

```bash
npm install
npm run lint
```

После изменений в `src/` проверьте типы и пересоберите production-скрипт:

```bash
npm run build:ts
```

## Устройство проекта

- `public/` — HTML-страницы, стили, клиентские модули и изображения.
- `src/` — TypeScript-логика фотоальбома: загрузка списка с сервера, критерии, фильтрация и отображение.
- `public/js/main.js` — минифицированный production-бандл фотоальбома; генерируется командой `npm run build:ts`.
- `server/` — точка входа (package main): конфиг, маршруты, база, логгер, авторизация.
- `server/internal/store/` — единое хранилище сайта: одна SQLite-база `site.db`, версионированные миграции (`server/internal/store/migrations/`), весь SQL (пользователи, сессии, счётчик визитов, журнал действий, заявки с формы) и перенос старого счётчика из `visits.dat`. Тесты — в `server/internal/store/test/`.
- `server/internal/auth/` — закрытый раздел: регистрация, авторизация, сессии и сброс пароля (Go; хранение — через интерфейсы поверх `store`).
- `server/internal/album/` — фотоальбом: метаданные снимков из базы, приём и обработка загрузок (ресайз, WebP), отдача файлов и закрытая страница `/vault/album`.
- `server/internal/logging/` — центральный логгер (slog) и дублирование действий пользователей в журнал.
- `server/internal/webutil/` — общие HTTP-мелочи: реальный адрес клиента за nginx и централизованные лимиты частоты (реестр `Limits`, таблица бюджетов — в `main`).
- `scripts/` — вспомогательные скрипты.

## Хранилище данных

Все данные сайта — в одной SQLite-базе `DATA_DIR/site.db` (в проде
`/var/www/9site/var/site.db`): пользователи, сессии и токены сброса пароля,
счётчик визитов, журнал действий, заявки с публичной формы Sign Up и
метаданные снимков фотоальбома.
Драйвер — чистый Go без CGO, режим WAL. Схема — версионированные
миграции в `server/internal/store/migrations/` (`NNNN_описание.sql`, каждая в своей
транзакции, контрольные суммы в таблице `schema_migrations`); новое
изменение схемы — новый файл, существующие не правятся. Файлы
аватаров, загруженных снимков и исходящих писем живут рядом, в
`DATA_DIR/avatars/`, `DATA_DIR/photos/` и `DATA_DIR/outbox/`: база хранит
только метаданные, поэтому снимок базы на деплое остаётся маленьким. Кадр
загрузки ужимается до 1600 px по длинной стороне и пересохраняется в WebP;
анимированный GIF сохраняется байт в байт, чтобы не потерять анимацию:
ужать его нельзя, поэтому GIF шире 1600 px не принимается. Присланная
картинка проверяется по заголовку до декодирования (до 12000 px по стороне
и 60 Мпикс), чтобы маленький файл не развернулся в гигабайты памяти.
EXIF не читается: кадр с телефона может лечь боком.

Разделы фиксированы списком `album.Sections` (техника, гараж, tux, музыка,
прочее): в форме это выпадающий список, придумать новый раздел нельзя никому,
для этого нужен релиз. Всё, что шире пяти разделов, живёт в тегах.

Теги лежат в базе отдельными таблицами: `tags` (список известных) и
`photo_tags` (что на каком кадре). Тег виден в фильтре и форме, пока висит
хоть на одном кадре: опечатка не остаётся в витрине навсегда. Их список приходит витрине вместе со
снимками, поэтому новый тег появляется строкой в таблице, а не правкой
фронта. На кадр вешается до пяти тегов; набор берётся из базы, а новый тег
заводит только админ при загрузке. На витрине теги видны на карточке и
участвуют в фильтре (`#тег`), у засева тегов нет.

### Пределы и где они прописаны

Одни числа заданы кодом, частоты — таблицей бюджетов в `server/main.go`
(порог можно поднять переменной `LIMIT_<БЮДЖЕТ>`).

| Что                         | Предел                     | Где                                      |
| --------------------------- | -------------------------- | ---------------------------------------- |
| файл снимка                 | 5 МБ                       | `album/upload.go`, `maxPhoto`            |
| тело формы загрузки         | 6 МБ                       | `album/upload.go`, `maxBody`             |
| подпись кадра               | 100 символов               | `album/upload.go`, `maxName`             |
| раздел (слаг)               | 2-30, `[a-z][a-z0-9-]*`    | `album/upload.go`, `albumSlug`           |
| сохранённый кадр            | 1600 px по длинной стороне | `album/image.go`, `maxSide`              |
| присланный кадр             | 12000 px, 60 Мпикс         | `album/image.go`, `maxUploadSide/Pixels` |
| аватар                      | 512 КБ                     | `auth/users.go`, `maxAvatar`             |
| логин / пароль              | 3-30 / 8-72 символа        | `auth/users.go`, `loginPattern`          |
| сессия / ссылка сброса      | 30 дней / 1 час            | `auth/auth.go`, `sessionTTL`, `resetTTL` |
| аккаунтов на странице прав  | 200                        | `auth/roles.go`, `usersLimit`            |
| загрузки, вход, регистрация | 20 за 10 мин               | `main.go`, таблица бюджетов              |
| заявка с витрины            | 5 за 10 мин                | `main.go`, `leads.BudgetSignup`          |

При первом старте счётчик из старого `visits.dat` (на деплое это
единственные прежние данные) переливается в базу, а файл
переименовывается в `*.bak`. Сайт по-прежнему — один бинарник.

### Резервные копии и откат

```bash
site-server backup /путь/к/site-копия.db
```

Снимок снимается на работающей базе (SQLite `VACUUM INTO` — данные и WAL
переносятся согласованно, останавливать сервис не нужно) и не перезаписывает
существующий файл. Деплой делает такой снимок автоматически перед каждым
рестартом в `$DATA_DIR/backups/` (хранит последние 10 копий) — именно он и
является откатом: миграции накатываются при старте бинарника, поэтому копия,
снятая после рестарта, уже бесполезна. Каждый коммит — отдельный релиз в
`$DEPLOY_PATH/releases/<sha>`, сервис запущен через симлинк `current`, и
откат переносит ссылку на прошлый релиз вместе с его базой, а не переставляет
бинарник на месте.

## Закрытый раздел и авторизация

Пароли хранятся bcrypt-хэшем, сессия — cookie с случайным токеном
(в базе только его sha256), все запросы к базе параметризованы, вывод
экранируется через `html/template`.

Восстановление пароля шлёт письмо со ссылкой `/reset?token=…`. Если SMTP не
настроен, письмо сохраняется в `DATA_DIR/outbox/` (ссылка на экране —
только для запросов с самого сервера). Почта настраивается двумя способами:
пресетом популярного провайдера или своим SMTP-сервером. У Gmail, Яндекса
и Mail.ru нужен **пароль приложения**, а не обычный пароль аккаунта.
Переменные окружения:

| Переменная                      | Назначение                                                   |
| ------------------------------- | ------------------------------------------------------------ |
| `DATA_DIR`                      | обязателен: каталог базы, аватаров и писем                   |
| `BASE_URL`                      | внешний адрес сайта для ссылок в письмах                     |
| `SMTP_PROVIDER`                 | пресет почты: `gmail`, `yandex`, `mailru`                    |
| `SMTP_HOST`, `SMTP_PORT`        | свой SMTP-сервер (вместо `SMTP_PROVIDER`)                    |
| `SMTP_USER`, `SMTP_PASS`        | учётная запись или пароль приложения                         |
| `SMTP_FROM`                     | адрес отправителя писем                                      |
| `ADMIN_LOGIN`, `ADMIN_PASSWORD` | секретный админ: создаётся или обновляется при каждом старте |
| `LOG_LEVEL`, `LOG_FORMAT`       | уровень и формат лога (info, text\|json)                     |
| `LIMIT_<БЮДЖЕТ>`                | порог лимита частоты, напр. `LIMIT_AUTH_LOGIN=50`            |

Роли простые: `admin` грузит кадры в общий альбом, удаляет их и выдаёт
права на `/vault/users`, `user` грузит свои кадры и правит профиль. Последнего
админа снять нельзя. Резервный вход задаётся в `deploy.env`:

```sh
ADMIN_LOGIN=owner
ADMIN_PASSWORD=пароль-подлиннее-восьми-символов
```

При каждом старте сервер создаёт этот аккаунт или обновляет ему роль и хэш
пароля: пароль из окружения переживает потерю доступа, но и смена пароля
через интерфейс тоже не переживёт рестарт. Задавать надо оба поля, иначе
сервис не поднимется.

Лимиты частоты централизованы: один реестр (`webutil.Limits`), вся таблица
бюджетов — одним блоком в `server/main.go` и печатается в лог при старте.
Бюджеты: `auth.login`, `auth.register`, `auth.forgot`, `form.signup`,
`album.upload`.
Имя переменной — бюджет в верхнем регистре с точками на подчёркивания;
переопределяется только порог, окно (10 минут, у заявок — тоже 10) остаётся
константой. Неверное значение не роняет сервер — берётся дефолт и пишется
warn. Мелочь, но полезная: при исчерпании лимита ответ несёт `Retry-After`
со сколько ждать.

Пример для `deploy/deploy.env` на сервере: `SMTP_PROVIDER=gmail`,
`SMTP_USER=you@gmail.com`, `SMTP_PASS=<пароль приложения>`. Хост и порт
подставятся сами, копия каждого письма всё равно ляжет в outbox. Нерабочий
конфиг (неизвестный провайдер, логин без сервера) роняет запуск сразу, а
не при первом сбросе пароля.

Файл на сервере (`$DEPLOY_PATH/deploy.env`, режим 0600) принадлежит серверу:
деплой кладёт туда значения из репозитория только пока файла нет, а дальше
печатает расхождения и файл не трогает. Поэтому пароль задаётся один раз
на сервере (`$DEPLOY_PATH/deploy.env`), а не в git и не в секретах GitHub;
после правки хватает рестарта юнита, `EnvironmentFile` читается при старте.

Проверка: `go test ./... -race` — авторизация (регистрация, вход, закрытый раздел,
выход, смена данных, сброс пароля, SQL-инъекции, XSS, аватары), фотоальбом
(выдача списка, загрузка, ресайз, отказ чужим именам и не-картинкам, удаление),
хранилище (схема, импорт, счётчик, сессии, снимки базы), белый список статики
и ограничитель частоты.
